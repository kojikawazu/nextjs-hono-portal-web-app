# IaC（Infrastructure as Code）

## state はリモート backend に置く

**state をローカルファイルだけに置かない。** リモート backend（GCS / S3 等）を必ず設定する。

- `.gitignore` に `terraform.tfstate` を入れる**だけで終わらせない**。除外は正しいが、それは「どこに置くか」まで決めて初めて完結する。
- ローカル state は、**環境の入れ替え・PC の故障・リポジトリの再クローンで失われる**。state を失うと既存リソースを認識できないまま `apply` することになり、**リソースの重複作成や不整合**を招く。
- **backend 設定そのものはコミットする**（`backend` ブロックは秘密情報ではない）。

| ファイル | Git | 置き場所 |
|---|---|---|
| `*.tf`（定義） | コミットする | リポジトリ |
| `backend` 設定 | コミットする | リポジトリ |
| `terraform.tfstate` | **除外する** | **リモート backend** |
| `terraform.tfvars` | **除外する**（秘密情報を含む） | 各自のローカル + **変数一覧をドキュメント化** |

**除外するファイルは、必ず「代わりの置き場所」とセットで決める。** `.gitignore` の判断を「秘密かどうか」だけで行うと、秘密ではないが除外すべきもの（state）が行き場を失う。`terraform.tfvars` を除外する場合は、**必要な変数名の一覧をドキュメントに残す**（値は書かない）。

## 「壊れても誰も気づかない」状態を作らない

**IaC が実際の変更経路から外れていると、state が失われても何も壊れず、誰も気づかない。**

- デプロイや設定変更を IaC 以外の経路（CLI コマンド・CI の直接操作・管理コンソール）で行っている場合、**IaC は「適用されない定義」になる**。定義と実態の乖離は、次にインフラを変更しようとした瞬間に初めて表面化する。
- **どの変更をどの経路で行うかを決めて文書化する。** 経路が複数あるなら、**どちらが正か**を明記する。
- 同じ設定を 2 箇所（例: サービス側の環境変数と、イメージに焼いた `.env`）で持たない。持つなら**優先順位を明記**する（`duplication.md`「同じ知識を 2 箇所に持たない」）。

これは `duplication.md` の「CI は README を読まないので、README が腐っても CI は緑のまま」と同じ構造である。**検知する仕組みが無い乖離**は、規律ではなく構造で塞ぐ。

## 適用前の確認

- **`plan` の差分が空であることを定期的に確認する。** 差分が出るなら定義と実態が乖離している。
- **state を失った状態で `apply` しない。** 復元（`import`）が先。
- 破壊的な差分（`destroy` / `replace`）が出た場合は、**何が消えるかを読んでから**実行する。

## レビュー観点

- backend 設定がコミットされているか。ローカル state のままになっていないか。
- `.gitignore` で除外したファイルについて、**代わりの置き場所が決まっているか**（state はリモート backend、tfvars は変数一覧のドキュメント）。
- IaC が実際の変更経路に乗っているか。乗っていないなら、その旨と理由が記録されているか。
- 同じ設定が IaC と別経路の両方で管理されていないか。あるなら優先順位が明記されているか。
