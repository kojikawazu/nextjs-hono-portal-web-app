# DryRun（事前検証）と本登録

**DryRun とは「本登録とまったく同じ検証を、永続化せずに実行する」こと。** 検証が本登録より緩ければ「通ったのに登録できない」、厳しければ「通らないのに登録できる」。どちらも DryRun の存在価値を失わせる。

本ルールは DryRun を持つ API に共通の意味論を定める。**スタック固有の実装手段**（検証機構の当て方・応答ステータス・検証専用エンドポイントを立てない根拠）は各スタックの `api.md` が持つ。

## 経路の形

**両経路は同じ入口・同じ検証を通り、分岐するのは永続化の有無だけ。**

```
DryRun :  ハンドラ（形式検証）─┐
                               ├→ 集約 Validator → 個別検証 A, B, C
本登録 :  ハンドラ（形式検証）─┘
                                  └→ 永続化（本登録のみ）
```

- **形式・構文の検証は入口のスキーマ**で両経路共通にする。経路ごとにスキーマがズレる事故を構造的に防ぐ。
- **スキーマで書けない業務ルールは集約 Validator に閉じる**。個々の検証を経路から直接呼ばない。
- **DryRun は本処理エンドポイントのモード**（`?dryRun=true` 等）として実装する（次節）。

## 検証専用エンドポイントを立てない

**DryRun は本処理エンドポイントのモード**（`?dryRun=true` 等）として実装する。`POST /<resource>/validate` のような**検証専用エンドポイントを別に立てない**。

立てる場合は、本処理と**同じスキーマ・同じ検証が当たることをどう担保するか**をルールとして書く。担保できないなら、モードとして実装する方が構造的に安全 — **同じハンドラを通る以上ズレようがない**。規律ではなく構造で担保する。

事故の実例: `POST /tasks/validate` を 1 本だけ用意し、作成フォームと編集フォームの両方がそこを叩いていた。専用エンドポイントは作成用スキーマ固定だったため、**編集フォームの事前検証が「作成用スキーマ」で行われていた**。「事前検証と本処理は同一ルール」と仕様に書いてあっても、**経路が別なら保証されない**（`api.md` の禁止例「同じ業務ルールを別経路に書き写す」と同じ構造の事故）。

## 集約 Validator

### なぜ「集約」するのか

個々の検証（A / B / C）を各経路から直接呼ぶと、**「どの検証を呼ぶか」の集合が経路ごとに持たれ、そこが新しい乖離点になる**。

```
悪い例: DryRun は A・B だけ呼び、あとから足した C を呼び忘れる
        → DryRun は通るのに本登録で落ちる
```

集約 Validator に集合を閉じ込めれば、**検証を 1 つ足すだけで両経路に自動で効く**。「検証を追加したら呼び出し側を全部直す」作業が発生しない状態にすることが目的。

### 置き場所

**両経路より下位（application 層以下）に置く。** DryRun の入口（presentation）と本登録の usecase（application）の双方から呼ばれるため、presentation に置くと `application → presentation` の逆流になり、`api.md` の「レイヤ依存の一方向ルール」に違反する。

### 業務検証を Usecase 本体に書かない

**DryRun 経路は Usecase を呼ばない**（入口 → 集約 Validator → 204）。したがって **Usecase 本体に直書きされた業務検証は、DryRun からは存在しないのと同じ**になる。

```
悪い例: Usecase の中に業務判断の if を直接書く
  execute(cmd):
    if (重複している) throw ...      ← DryRun からは見えない
    if (期限が過去) throw ...        ← DryRun からは見えない
    保存する

良い例: 検証は集約 Validator に置き、Usecase は順序と境界だけを持つ
  execute(cmd):
    集約 Validator.validate(cmd)     ← DryRun が呼ぶのと同じもの
    保存する
```

- **DryRun を持つエンドポイントの業務検証は、Usecase 本体に書かず集約 Validator に置く。** Usecase は「集約 Validator を呼ぶ → 永続化する」の順序とトランザクション境界だけを持つ。
- **既存コードに DryRun を後から足す場合は、先に Usecase 本体の業務検証を集約 Validator へ移す。** 移さないまま DryRun を足すと、足した時点で乖離が生まれる。
- **適用範囲は DryRun を持つエンドポイント**。DryRun を持たない usecase にまで Validator クラスへの分離を強制しない（`api.md` の担当レイヤ表どおり Usecase / ドメインモデルに置いてよい）。
- **トレードオフ**: 検証と永続化が別ファイルに分かれ、Usecase だけを読んでも「何が検証されるか」が見えなくなる。**Usecase の先頭で集約 Validator を 1 回呼ぶ**形を守り、呼び出しが処理の途中に埋もれないようにする。

### 本登録でも必ず通す

**「DryRun で検証済みだから」を理由に、本登録側の検証を省略しない。** クライアントが DryRun を呼ばないこともあれば、呼んでから時間が経っていることもある。**本登録は単体で完結して安全**でなければならない。

## 副作用の禁止範囲

**DryRun は業務状態を変えない。** 「永続化しない」だけでは足りない。

| 操作 | DryRun での扱い |
|---|---|
| DB の読み取り（重複チェック・参照整合性の確認） | **許可**。業務ルールの検証に必然 |
| 業務データの書き込み（INSERT / UPDATE / DELETE） | **禁止** |
| 採番・シーケンスの消費 | **禁止**（rollback しても戻らない） |
| 状態を変える外部 API 呼び出し（決済オーソリ・在庫引当・メール / 通知送信） | **禁止** |
| 参照系の外部 API 呼び出し（住所検索・マスタ照会） | **許可**。ただし課金・レート制限を本処理と同じだけ消費することを許容できる場合に限る |
| キュー / ジョブの投入 | **禁止** |
| キャッシュの更新・無効化 | **禁止**（キャッシュは業務状態の写像であり、DryRun が触ってよいものではない） |
| ファイル / オブジェクトストレージへの保存 | **禁止** |
| 監査ログ・アクセスログの記録 | **許可**（推奨）。「誰がいつ何を DryRun したか」は業務データの変更ではなく、追跡のために残す |
| レート制限カウンタの加算 | **許可**。DryRun を無制限に叩けると、後述の存在推測やコスト増の経路になる |

### 「トランザクションを張って rollback する」方式は既定では採らない

一見「本登録とまったく同じコードを流せて安全」に見えるが、次の理由で既定にしない。

- **rollback で戻らないものがある**: 採番・シーケンス、トリガから発火した外部連携、トランザクション外の外部 API 呼び出し、キャッシュ、ファイル出力。
- **本番トラフィックと競合する**: 検証のためだけに書き込みロックを取る。トランザクションが長いほど影響が大きい。
- **「rollback されるから安全」という前提が、後から副作用を足す人には見えない**。同じコードに 1 行足した瞬間に破れる。

**例外的に採ってよいのは、DB 制約でしか判定できない検証を DryRun に含める必要がある場合**に限る。採る場合は次の 3 つを満たす:

1. そのトランザクション内で外部 API を呼ばない
2. 採番・シーケンスが消費されることを許容すると明記する
3. **必ず rollback されることをテストで担保する**（例外経路を含む）

## 認可

**DryRun も本処理と同じ認可（Guard / ミドルウェア）を通す。**

通さないと、**応答の差で他人のリソースの存在や値を推測できる**（存在しない ID なら 404、存在するが重複なら 422 — この差が情報になる）。DryRun は「まだ何も変えていない」ので緩めたくなるが、**読み取りと応答内容そのものが漏洩経路**になる。

認可は「検証」ではなく**アクセス制御**なので、集約 Validator ではなく**ハンドラ手前**（Guard / ミドルウェア）に置く。`api.md` の「バリデーションの二重定義禁止」の対象外。

## TOCTOU（DryRun 成功 ≠ 本登録成功）

**検証した時点と登録する時点の間に、DB の状態は変わる。** 重複チェックを通した直後に、他人が同じ値を登録し得る。

- **DryRun の応答は「本登録が成功する」という約束ではない。** API 仕様書やレスポンスの表現でそう読ませない。
- **最終防衛は DB 制約**（UNIQUE / NOT NULL / 外部キー）。アプリ側の検証をすり抜けた同時実行はここで落ちる。`api.md` の担当レイヤ表と同じ考え方。
- **クライアントは本登録の失敗ハンドリングを必ず持つ。** 「DryRun が通ったから」を理由に、本登録のエラー表示を省略した UI を作らない。
- **本当に「必ず成功する」ことが要件なら、DryRun では解けない。** 予約・一時確保（在庫の引当・番号の仮押さえ）という別の機能が必要になる。DryRun をその代わりに使わない。

## リクエストの組み立ては 1 箇所にする

検証が同じでも、**検証される値の作られ方が経路ごとに違えば同じ乖離が起きる**（`api.md` の「リクエストの受け渡し」により、入力から Command への詰め替えが発生するため）。

`?dryRun=true` を**同じハンドラのモード**として実装していれば組み立ては 1 回で済み、この問題は起きない。**別ハンドラに分けた場合だけ**、組み立てが 2 箇所になって乖離点が生まれる。

## レビュー観点

- DryRun 経路と本登録経路が、**同じスキーマ**と**同じ集約 Validator**を通っているか
- 個々の検証を経路から直接呼んでいないか（呼んでいたら、検証を足したとき片方に入れ忘れる）
- **Usecase 本体に業務判断の `if` が残っていないか**（DryRun からは見えない検証になる）。形式チェックとの区別は「**DB 参照・外部状態の照会が要るか**」で付ける — 要るなら業務ルールなので集約 Validator 側
- 集約 Validator が presentation 層に置かれていないか（レイヤ逆流）
- DryRun 経路に、上表で禁止した副作用が入っていないか。特に**キャッシュ更新・キュー投入・通知送信**は「永続化ではない」ため見落としやすい
- DryRun が認可を通っているか。本処理とレスポンスの粒度が揃っているか
- 本登録側が、DryRun 済みを前提に検証を省略していないか
